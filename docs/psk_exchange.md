# AEGIS — ручной обмен ключом контейнера (PSK), P4 · §6.2 / §10.3

> Контракт согласования клиент (`aegis-client`) ↔ сервер (`aegis-server`), §0.
> Клиентская реализация: `rust/aegis-core/src/psk.rs` (примитивы),
> `crypto/.../PskCrypto.kt` (фасад), `data-storage/.../PskStore.kt` (хранение),
> `app/.../psk/PskManager.kt` + `app/.../ui/psk/*` + `app/.../nfc/*` (UX/NFC).

## 1. Главный инвариант (zero-trust к серверу)

**PSK (ключ каскадного контейнера, слой A) НИКОГДА не передаётся по сети.**

Этот документ описывает ЛИЧНЫЙ обмен. Второй путь — удалённое добавление
контакта (`docs/contact_requests.md`), где секрет слоя A тоже не передаётся, но
**выводится** из подписанного рукопожатия на обеих сторонах независимо. Инвариант
«PSK не уходит в сеть» сохраняется в обоих случаях; различается то, на чём
держится уверенность в личности собеседника (см. `ContactTrust`).

Личный обмен — СТРОГО вручную и вне сети (out-of-band), одним из способов:

- **QR лично** — показ с `FLAG_SECURE` (§14.3), автоскрытием QR по таймеру (60 с)
  и предупреждением «показывать только лично». Сканирование — открытой
  библиотекой ZXing (zxing-android-embedded), локально; её экран сканера
  (`CaptureActivity`) `FLAG_SECURE` не ставит. Оба телефона показывают свои
  половины одновременно, поэтому один снимок или видео обоих экранов даёт PSK
  целиком (`FLAG_SECURE` от внешней камеры не защищает). **Единственный способ,
  который сейчас работает в приложении.**
- **Ручной ввод мнемонической фразы** (BIP-39-подобной, 24 слова для 256-бит PSK) —
  **не выведен в интерфейс**: кодирование есть в ядре (`psk.rs`), но экрана ввода
  и вызова импорта в приложении нет.
- **NFC при касании** — HCE-обмен между двумя устройствами (роль «карты» — тот,
  кто показывает ключ; роль «ридера» — принимающий). Полностью локально.
  **Работает только отдающая сторона:** ридер (`nfc/PskNfcReader.kt`) нигде не
  создаётся, поэтому два телефона AEGIS по NFC обменяться не могут. При этом HCE
  отдаёт полную нагрузку (половину PSK, `accountId`, identity и бандл) открытым
  текстом любому ридеру рядом, пока открыт экран обмена.

Следствия для `aegis-server`:

- Сервер **не участвует** в обмене PSK и **не хранит** PSK.
- В сеть (а значит на сервер) попадает только **контейнер слоя A** —
  непрозрачный BLOB (см. `docs/layer_a_container_format.md`). Сервер не может его
  расшифровать: `container_secret` (PSK) у него нет и не будет.
- Даже полностью скомпрометированный сервер, контролирующий раздачу публичных
  ключей слоя B, не раскрывает контент слоя A (§10.7).

## 2. Хранение PSK на устройстве

- PSK лежит ТОЛЬКО в защищённом хранилище: файл `psk_store.aegis` дополнительно
  оборачивается аппаратным ключом Keystore/StrongBox (`KeyStoreManager.wrap`).
- В **буфер обмена PSK не копируется** никогда.
- Отпечаток PSK (`HKDF-SHA512`, необратимый) хранится рядом и служит для
  **повторной сверки** сторонами без раскрытия секрета.
- Экстренная очистка (§7.4) уничтожает мастер-ключ Keystore → все PSK становятся
  нечитаемым мусором (crypto-shredding); файл PSK-стора дополнительно удаляется.

## 3. Формат полезной нагрузки обмена (QR / NFC)

JSON (`core-common/.../psk/PskModels.kt` → `PskExchangePayload`, v2):

```json
{
  "t": "aegis-psk",
  "v": 2,
  "pskB64": "<base64 256-бит PSK — секрет слоя A>",
  "fromAccountId": "aegis:<hex>",
  "fromFingerprint": "<hex identity safety number>",
  "label": "aegis:<short>",
  "identityB64": "<base64 публичного identity-ключа слоя B>",
  "bundleJson": "<publ. prekey-бандл X3DH/PQXDH (§0) — публичные ключи слоя B>"
}
```

- `t`/`v` — маркер типа и версия (отличает наш код от посторонних при сканировании).
- `pskB64` — **сам секрет**; появляется только в QR/NFC, показываемых лично.
- `fromAccountId` / `fromFingerprint` — привязка PSK к контакту и ручная сверка
  identity (safety number, §6.2). Мнемонический способ этих полей не несёт.
- `identityB64` / `bundleJson` (v2) — публичные данные слоя B: позволяют
  собеседнику СРАЗУ установить Signal-сессию (X3DH/PQXDH) без сети. PSK в KDF
  PQXDH не входит — см. §4. Опциональны.

### QR против NFC: размер бандла

`bundleJson` содержит Kyber1024 prekey (PQXDH, ~1568 байт → ~2.9 КБ полной
нагрузки в base64), что **не помещается в один QR-код**. Поэтому:

- **QR** несёт КОМПАКТНУЮ нагрузку — тот же JSON, но с пустым `bundleJson`
  (`PskGenerated.qrPayloadJson`): PSK + identity + привязка к контакту. QR всегда
  рендерится и остаётся легко сканируемым.
- **NFC** несёт ПОЛНУЮ нагрузку (`PskGenerated.payloadJson`, включая бандл):
  APDU-транспорт чанкирует данные (≤240 байт на блок), лимита размера нет —
  поэтому именно NFC задуман для мгновенного установления сессии слоя B (пока
  приём по NFC не подключён, бандл всегда догоняется по каналу `keyx`).
- **Мнемоника** несёт только PSK (слой A), без полей привязки и бандла (в
  интерфейс не выведена).

Этот JSON **никогда** не сериализуется в сетевой запрос. Он живёт только:
на экране (QR), в NFC-APDU при касании, либо вводится как мнемоника.

### NFC (HCE) транспорт

- AID: `F0416567697350534B` (`0xF0` + `"AegisPSK"`), см. `res/xml/psk_apduservice.xml`.
- Протокол: `SELECT AID` → повторные `READ` (`80 B0 <block> 00 00`), ответ —
  chunk (≤240 байт) + `SW 9000`; пустой chunk = конец. Payload — тот же JSON.
- Аутентификации ридера и шифрования нет; нагрузка выставляется на всё время
  жизни экрана обмена. Уникальный AID позволяет NFC-ридеру опознать приложение.

### Догоняющий обмен бандлом: канал `keyx`

QR не несёт бандл, а `bundleId` помогает только если релей доступен В МОМЕНТ
обмена — при личной встрече Tor часто ещё не поднят. Раньше это было тупиком:
контакт оставался с `bundle_json = NULL`, слой B не стартовал, и каждая отправка
падала в `FAILED` («ошибка E2EE»). Догнать бандл было нечем — control-канал
(`ControlChannel`, `DeviceAnnouncer`) сам шифруется слоем B, то есть требует уже
установленной сессии.

Канал `keyx` (`KeyExchangeChannel`) разрывает этот круг: он идёт поверх ОДНОГО
слоя A. Так можно, потому что PSK получен личным жестом и в сеть не уходил, а
каскад слоя A — AEAD. Значит конверт `keyx`:

- серверу не читается и не подделывается;
- аутентифицирован «личной встречей»: положить конверт в per-device mailbox
  (адрес выводится из PSK, `multidevice.md` §4.1) и снять с него слой A может
  только владелец PSK.

Наружу едут ТОЛЬКО публичные `identityB64` + `bundleJson`; PSK по-прежнему не
уходит в сеть. Доставленный так бандл доверенне скачанного с релея по `bundleId`:
там анти-MITM держится на сверке identity, здесь — на самом PSK. Обратная
сторона: канал `keyx` защищён ровно настолько, насколько секретен PSK (см.
ограничение ниже).

Раунд симметричен (начать может любая сторона):

```
 A ──[keyx keyx-request:  identity_A + bundle_A]──▶ B    B сохраняет ключи A
 A ◀──[keyx keyx-announce: identity_B + bundle_B]── B    A сохраняет ключи B
```

- Конверт: `{ciphertextB64, senderDevice, channel:"keyx", v}` — демультиплексируется
  в `RelayReceiver.dispatch` по полю `channel`, как `call` и `control`.
- Нагрузка (внутри слоя A): `{type, deviceId, identityB64, bundleJson, atMs, v}`.
- `keyx-announce` — ответ на запрос, повторно не просит (иначе пинг-понг).
- Если identity контакта уже закреплён лично (пришёл в QR/NFC), присланный бандл
  должен приниматься ТОЛЬКО при совпадении `identity_key`, иначе отбрасываться.
  Если закреплённого нет, первый принятый бандл сам становится закреплённым (TOFU).
- **Известная ошибка (аудит 01.11.2026):** бандл без поля `identity_key`
  считается совпавшим (`PrekeyBundle.identityMatches`), после чего присланный
  identity перезаписывает закреплённый (`ContactStore.setPeerKeys`, COALESCE).
  Номер устройства в нагрузке (`deviceId`) задаёт сам отправитель, и для нового
  номера закреплённого identity нет вовсе — устройство создаётся с присланным
  ключом и сразу попадает в fan-out. Поэтому тот, кто знает PSK пары и оба
  `accountId`, может положить конверт `keyx` в ящик жертвы и зарегистрировать
  «устройство» собеседника со своим Signal-ключом (`docs/threat-model.md` §3.1).
- Закреплённый identity устройства (`StoredContact.identityFor`) передаётся и в
  само ядро Signal на каждую операцию (`Store::pin_identity` в `signal.rs`):
  libsignal отвергает бандл, PreKey-сообщение и сессию на другом ключе. Так сервер
  не может первым завести с нами сессию «от контакта» на своём ключе и тем самым
  отравить TOFU, а уже отравленное состояние лечится при следующем обмене: чужая
  сессия перестаёт считаться действующей и заменяется новой по сверенному бандлу.
- Поводы отправки: обмен только что состоялся; отправка упёрлась в отсутствие
  ключей (`MessagePipeline.onMissingPeerKeys`); кнопка «Повторить» в баннере
  чата; периодический цикл добора (персональный backoff 20 с → 15 мин, чтобы не
  забивать ящик офлайн-собеседника).
- Когда ключи приехали, поднимается индикатор E2EE и автоматически до-отправляются
  сообщения, упавшие в `FAILED` из-за их отсутствия.

## 4. Связь PSK со слоем A и слоем B

- **Слой A:** `PskManager.cipherFor(contactId)` берёт PSK контакта и
  создаёт `CryptoModule.createCascadeCipher(psk)` — PSK является `container_secret`
  (HKDF-SHA512 → K1..K4, см. формат контейнера).
- **Слой B — не хук в KDF PQXDH.** Публичный API libsignal не даёт подмешать PSK
  внутрь `process_prekey_bundle`. Форкать аудированную библиотеку нельзя (§1).
  Поэтому PSK связывается с сессией двумя отдельными конструкциями в `signal.rs`:
  1. `psk_session_binding` — `HKDF-SHA256(salt=PSK, ikm=sort(idA‖idB),
     info=aegis/psk-x3dh-binding/v1)` → safety-code для сверки identity.
  2. `psk_session_seal` / `psk_session_open` — ChaCha20-Poly1305 на ключе
     `HKDF-SHA256(salt=PSK, ikm=sort(idA‖idB), info=aegis/psk-session-seal/v1)`
     вокруг plaintext **до** `message_encrypt`. Формат провода:
     `A1S1 || nonce(12) || ciphertext||tag`. Без PSK и без тех identity, которые
     сторона реально увидела, payload не вскрыть, даже если слой A снят.
     Конверты без метки `A1S1` принимаются (совместимость); конверт с меткой и
     провалом тега отвергается (fail-closed). Если PSK и identity есть, а seal
     не удался — отправка прерывается, silent-downgrade нет. Обёртка применяется
     к сообщениям переписки; сигналинг звонков и control-канал идут без неё
     (слои A + B).
- **Бутстрап слоя B слоем A:** если бандл при обмене не доехал, он догоняется по
  каналу `keyx` — единственному каналу БЕЗ слоя B (см. §3). Флаг
  `contacts.session_ready` поднимается по факту `processBundle`
  (`SignalSessionManager.onSessionEstablished`).

## 5. Что должен (и не должен) делать backend

Должен: транспортировать контейнер слоя A как opaque BLOB внутри конверта слоя B;
не логировать содержимое (§7.6).

Не должен: принимать, хранить, пересылать PSK; зависеть от структуры контейнера
(кроме факта «это бинарный BLOB»); пытаться его расшифровать.
