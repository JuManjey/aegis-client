# AEGIS — мультидевайс: протокол per-device сессий, device-linking и fan-out

> Статус: **клиентские Этапы 1–5 реализованы и верифицированы инструментальными
> тестами** (§1.32–§1.37); протокольные follow-up'ы варианта №2 ЗАВЕРШЕНЫ:
> self-sync-отзыв (№2.1, §1.37), control/звонки на per-device v2 (№2.2, §1.38 —
> см. §6.1), forward secrecy self-sync (№2.3, §1.39 — см. §6.2). Плюс усиление
> приватности fan-out: смягчение тайминг-корреляции (`FanoutJitter`, §1.40) и
> прикрытие факта/объёма отправки cover-traffic'ом (`CoverTraffic`, §1.41 — №3a) —
> см. §12. Backend не менялся. Документ — источник истины по multi-device
> (требования — §7.1.1/§7.1.2 технического задания).

Требование владельца (§7.1.1): пользователь может **разрешить использование
аккаунта на нескольких устройствах одновременно** (по умолчанию — запрет,
безопаснее). До сих пор `multiDeviceAllowed` был лишь клиентским флагом-политикой
(§1.23), а фактическая работа второго устройства не была реализована: перенос
аккаунта (§1.31) нацелен на *миграцию/слияние*, а не на *параллельную* работу.

Этот документ описывает, как несколько устройств одного аккаунта работают
**параллельно**, не нарушая ни одного крипто-инварианта AEGIS.

## 1. Почему НЕ «общий Double Ratchet»

Самое очевидное (и **неверное**) решение — синхронизировать между устройствами
единый Signal-blob (identity + храповики Double Ratchet). Это ломается сразу:

- **Рассинхрон храповика.** Double Ratchet — это КС-автомат с однонаправленным
  продвижением: каждое шифрование/расшифрование мутирует цепочки ключей. Если два
  устройства делят один храповик, любое сообщение, обработанное на устройстве A,
  сдвигает состояние так, что реплика на устройстве B становится невалидной →
  сообщения перестают расшифровываться, forward secrecy нарушается.
- **Гонки.** `SignalStateManager` уже помечен `@Synchronized` именно потому, что
  одновременная мутация одного blob = потеря храповика. Между устройствами такой
  замок невозможен.
- **§1.31 это уже фиксирует.** Слияние переноса осознанно НЕ переносит
  `signalStateB64` (иначе рассинхрон). Тот же принцип масштабируется здесь.

**Вывод (инвариант MD-1):** каждое устройство — самостоятельный Signal-эндпоинт со
СВОИМ identity и СВОИМ Double Ratchet. Общего ratchet-состояния между устройствами
нет никогда.

## 2. Инварианты, которые нельзя нарушать

| # | Инвариант | Источник |
|---|-----------|----------|
| MD-1 | Каждое устройство — отдельный Signal identity + отдельный ratchet | §1, §6.1 |
| MD-2 | Сервер остаётся «тупым» store-and-forward, zero-trust: должен видеть только opaque mailbox-id + шифртекст (сейчас видит и открытые поля конверта — см. §12) | §7.6, §10.9 |
| MD-3 | PSK не уходит в сеть; всё, что видит сервер — производные HKDF | §6.2, P4 |
| MD-4 | Секреты линковки/синхронизации передаются вне сети (QR/файл), зашифрованы | §7.1.2, §1.23 |
| MD-5 | Свою криптографию не пишем: HKDF-SHA512, libsignal, каскад слоя A | §1 |
| MD-6 | Слой A (каскад на PSK) остаётся неизменным; multi-device живёт в слое B + адресации | §4, §5 |
| MD-7 | Жёсткий потолок хранения 7 дней распространяется и на mailbox устройств | §7.3 |

## 3. Модель устройства

Аккаунт = мнемоника (§7.1) → детерминированный `accountId` (`aegis:<hex>`),
одинаковый на всех устройствах. Поверх аккаунта вводится **устройство**:

```
Device {
  deviceId : u32   // стабильный в пределах аккаунта, 1..=255 (ограничение ProtocolAddress::DeviceId = u8)
  signalIdentity   // СВОЙ Signal identity keypair (создаётся локально, НЕ из мнемоники)
  prekeyBundle     // СВОИ prekeys (публикуются вне сети / через self-sync)
  label            // человекочитаемое имя («Пиксель», «Планшет»)
  linkedAtMs
}
```

- `deviceId = 1` — **первичное** устройство (обратная совместимость: сегодня всё
  захардкожено на 1). Линкованные устройства получают `deviceId ∈ 2..=255`,
  назначаемый первичным при линковке (счётчик в реестре своих устройств).
- Signal identity устройства **не выводится из мнемоники** — он случайный, как
  сейчас (`stateful::create_account` генерирует случайный `IdentityKeyPair`).
  Поэтому два устройства одного аккаунта уже имеют разные Signal-identity —
  это естественная основа для per-device сессий.
- `ProtocolAddress` в libsignal = `(name, deviceId)`. Мы используем
  `name = accountId`, `deviceId = deviceId`. Peer держит отдельную сессию с
  каждым `(accountId, deviceId)` — libsignal это уже поддерживает
  (`remote_device` — параметр). Захардкожен только ЛОКАЛЬНЫЙ device id
  (`LOCAL_DEVICE_ID`), что и снимается на Этапе 1.

**Ограничение диапазона.** libsignal `DeviceId` — это `u8` (см. `signal.rs::addr`),
поэтому на аккаунт до 255 устройств. Для мессенджера с ручной линковкой это с
большим запасом.

## 4. Криптографическая адресация: mailbox v2 (per-device)

Сегодня (v1) mailbox выводится из PSK и **роли** (0/1) — по одному входящему
подканалу на сторону переписки. Для мультидевайса нужен **входящий подканал на
устройство**, вычислимый и владельцем (чтобы слушать), и любым отправителем
(чтобы доставить).

### 4.1 Подканал переписки (conversation mailbox v2)

```
convInbox(PSK, ownerAccountId, ownerDeviceId) =
    HKDF-SHA512(
        salt = "AEGIS/mailbox/v2",
        ikm  = PSK,
        info = "aegis/mailbox/v2/conv/" + ownerAccountId + "/" + ownerDeviceId
    ) → 32 байта → url-safe base64 без паддинга
```

- Владелец устройства `(A, dA)` слушает `convInbox(PSK, A, dA)`.
- Любой отправитель, знающий `PSK` и адрес получателя `(A, dA)`, пишет туда же.
- Направленность встроена в scope (ящик принадлежит конкретному `(account,device)`),
  роль 0/1 больше не нужна — вместо неё accountId+deviceId.
- Сервер видит только 256-бит capability (MD-2/MD-3): id не связывается ни с
  accountId (он под HKDF, необратим), ни с рабочими ключами (разделение доменов
  от `AEGIS/mailbox/v1`, `AEGIS/psk/v1`, `AEGIS/cascade/v1`).

### 4.2 Подканал синхронизации своих устройств (self-sync mailbox)

Мои устройства должны обмениваться между собой (новые сообщения/контакты/PSK/
анонсы устройств). Для этого — отдельный секрет, общий ТОЛЬКО моим устройствам
(они делят мнемонику) и неизвестный контактам:

```
selfSyncSecret = HKDF-SHA512(salt="AEGIS/identity/v1", ikm=BIP39_seed,
                             info="aegis/self-sync/v1")   // 32 байта

selfSyncInbox(myAccountId, targetDeviceId) =
    HKDF-SHA512(salt="AEGIS/mailbox/v2", ikm=selfSyncSecret,
                info="aegis/mailbox/v2/self/" + myAccountId + "/" + targetDeviceId)
```

Так устройство `dX` шлёт синхронизацию устройству `dY` в `selfSyncInbox(X, dY)`,
а слушает `selfSyncInbox(X, dX)`. `selfSyncSecret` выводится детерминированно из
мнемоники, поэтому доступен каждому линкованному устройству без передачи по сети.

> Реализация Этапа 1: обобщённая `psk::mailbox_id_device(secret, scope, deviceId)`
> покрывает оба случая (conversation → `secret=PSK`, self-sync →
> `secret=selfSyncSecret`); `identity::derive_self_sync_secret` даёт секрет.

## 5. Device-linking (привязка нового устройства, вне сети)

Линковка переиспользует крипто-паттерн переноса аккаунта (§1.23/§1.31): пакет
шифруется паролем линковки (Argon2id 64 МиБ / 3 / 1 → каскад слоя A; пароль — от
8 символов) и передаётся **вне сети** (QR / файл), наружу — только
`TransferEnvelope`-подобный контейнер (MD-4). Пакет содержит мнемонику и все PSK,
поэтому снимок QR или копия файла позволяют перебирать пароль офлайн.

Отличие от переноса: линковка НЕ клонирует Signal-состояние (MD-1). Пакет несёт:

```
LinkPayload {
  mnemonic            // общий мастер-секрет аккаунта (тот же accountId)
  assignedDeviceId    // deviceId, выданный новому устройству первичным
  contacts[]          // без Signal-состояния: id + remoteIdentity + bundle + sessionReady=false
  psks[]              // ключи слоя A по контактам (нужны новому устройству)
  settings?           // опционально
  knownPeerDevices[]  // реестр устройств контактов (§7)
  primaryDeviceId, primaryLabel
}
```

Процедура:

1. Первичное устройство: «Привязать устройство» → вводит пароль линковки → выделяет
   новый `assignedDeviceId` (следующий свободный в реестре своих устройств) →
   собирает `LinkPayload` → показывает QR (или файл, `FLAG_SECURE`).
2. Новое устройство: сканирует → вводит пароль → распечатывает пакет →
   создаёт **свой** Signal identity (`create_account`) с `LOCAL_DEVICE_ID =
   assignedDeviceId` → сохраняет контакты/PSK/настройки → публикует свой
   prekey-бандл в self-sync (чтобы первичное узнало его identity).
3. Первичное устройство: получает анонс нового устройства по self-sync → добавляет
   его в свой реестр → **рассылает device-announce всем контактам** (по control-
   каналу переписки), чтобы контакты начали fan-out и на новое устройство.
4. Контакты: получают device-announce `(accountId, newDeviceId, identity, bundle)`
   → добавляют устройство в свой per-contact реестр (§7).

`multiDeviceAllowed=false` (по умолчанию) блокирует шаг 1 в UI с честным
предупреждением; включение требует явного подтверждения (§8, «ослабление»).

## 6. Fan-out доставки

Одно логическое сообщение доставляется во ВСЕ релевантные подканалы:

- **К устройствам контакта.** Для каждого известного устройства контакта `(B, dB)`:
  отдельная Signal-сессия `(localAccount, myDeviceId) → (B, dB)`, отдельный
  шифртекст, POST в `convInbox(PSK, B, dB)`. Разные шифртексты (каждый ratchet
  свой) — это неизбежная цена MD-1 (как в Signal sender-side fan-out).
- **К своим другим устройствам (self-sync).** Копия исходящего (и входящего)
  оборачивается в self-sync-конверт (Signal-сессия между моими устройствами) и
  постится в `selfSyncInbox(myAccount, otherDeviceId)` для каждого моего
  устройства ≠ текущего. Так вся история и состояние переписок сходятся на всех
  устройствах без общего ratchet.

Точки встраивания в существующий код:

| Точка | Файл | Изменение |
|-------|------|-----------|
| Шифрование | `SignalSessionManager.encryptTo` | per-device сессия/шифртекст; `localDevice` — параметр |
| Адресация | `PskManager.convMailboxFor` | per-device inbox v2 (v1 `mailboxPairFor` удалён) |
| Доставка | `RelayGateway.postToPeerDevices` | цикл POST в per-device подканалы устройств |
| Приём | `RelayReceiver.reconcile` | long-poll на свой per-device inbox + self-sync inbox |
| Контакт | `StoredContact.activeDevices()` | список устройств вместо одного `remoteDevice` |

Backend при этом **не меняется** (см. §9).

### 6.1 Control-канал и сигналинг звонков на per-device v2 (follow-up №2.2)

Переписка изначально живёт в per-device подканале v2, а control-канал (§14.2) и
сигналинг звонков (§7.5) поначалу оставались на общем v1-mailbox (роль 0/1). Это
давало **гонку деструктивного ack**: все мои устройства слушали ОДИН v1-ящик, и
ack любого из них удалял сообщения для остальных.

Follow-up №2.2 переводит control и звонки в тот же **per-device conversation-
mailbox** адресата, что и переписка:

- `ControlChannel.send`/`CallSignaling.send` делают тот же fan-out, что
  `MessagePipeline` (слой A один раз → per-device Signal-сессия → свой конверт →
  `RelayGateway.postToPeerDevices`). Звонок «поднимает» все устройства собеседника.
- Демультиплексирование каналов (`channel = "call" | "control" | сообщение`)
  происходит уже НА per-device подканале (`RelayReceiver.dispatch`). Отдельный
  mailbox под control/звонки не нужен — у каждого устройства свой ящик и свой ack,
  поэтому гонки больше нет (прямое следствие §9).
- Конверты несут `senderDevice`; приём (`onWire`) расшифровывает по ratchet
  устройства-отправителя (`SignalSessionManager.decryptFrom`, MD-1).
- v1-адресация в клиенте удалена (`PskManager.mailboxPairFor`,
  `RelayGateway.post`/`inboxFor`/`outboxFor`, v1-цикл в `RelayReceiver`);
  крипто-примитив `mailbox_id` v1 в ядре сохранён и не тронут.

### 6.2 Forward secrecy self-sync: слой B между своими устройствами (follow-up №2.3)

Изначально self-sync-пакеты (`msg`/`announce`/`revoke`) запечатывались ТОЛЬКО
каскадом слоя A на `selfSyncSecret` (§4.2). Секрет **долгоживущий** и
детерминированно выводится из мнемоники, поэтому у слоя A нет forward secrecy:
компрометация `selfSyncSecret` раскрывала бы **всю** историю self-sync (копии
сообщений, отзывы), а не только текущий момент.

Follow-up №2.3 добавляет self-sync тот же **второй слой (B)**, что и переписке
контакта — Double Ratchet поверх каскада, но между МОИМИ устройствами:

- `msg` и `revoke` идут двойным конвейером: слой A (каскад на `selfSyncSecret`,
  один раз) → слой B (СВОЯ Signal-сессия `(myAccount, myDevice) → (myAccount,
  targetDevice)`). Реализовано в `SelfSyncManager.fanOut` через тот же
  `SignalSessionManager.encryptTo(remoteAccountId = myAccountId, targetDevice,
  targetBundle, inner)`, что и fan-out контакту — remote-имя = МОЙ `accountId`,
  различается только `deviceId` (libsignal это поддерживает).
- Приём (`onWire` → `handleMessage`/`handleRevoke`) снимает слой B по ratchet
  устройства-отправителя (`decryptFrom(myAccountId, senderDevice, …)`, выбор по
  полю `sigType` конверта), затем слой A (каскад). Конверт `msg`/`revoke` без
  валидного слоя B (пустой/битый `sigType`) отвергается — downgrade к «каскад-
  only» невозможен.
- **`announce` осознанно остаётся каскадом слоя A** (bootstrap): Signal-сессию
  между моими устройствами как раз и поднимает анонс, доставляя identity+bundle.
  Анонс несёт лишь ПУБЛИЧНЫЕ ключи, поэтому forward secrecy для него не требуется
  (компрометация `selfSyncSecret` не раскрывает приватного контента из анонса).
- **Что это даёт (MD-1 + FS):** компрометация `selfSyncSecret` больше НЕ
  раскрывает self-sync-историю — она дополнительно защищена эфемерным
  ratchet-состоянием слоя B (свои устройства уже держат отдельные Signal-identity,
  §3). Double Ratchet даёт и post-compromise security. Устройства без анонса (нет
  bundle/сессии) пропускаются в fan-out и синхронизируются после device-announce.
- Крипто-ядро/backend НЕ менялись — это чистый слой B/адресация в клиенте (MD-6).

## 7. Реестр устройств контактов

Каждый клиент хранит per-contact список устройств собеседника:

```
PeerDevice { accountId, deviceId, identityB64, bundleJson, sessionReady, addedAtMs, revoked }
```

Наполнение:
- Начальное устройство — из `PskExchangePayload` (identity+bundle первого
  устройства, как сейчас).
- Новые устройства — из device-announce по control-каналу (§5, шаг 4) либо
  «ленивого» самоанонса: входящий конверт несёт `senderDeviceId`; неизвестное
  устройство добавляется как «ожидающее верификации».
- Удаление — из device-revoke по control-каналу (§10).

Fan-out идёт по всем `revoked=false` устройствам контакта — в том числе
непроверенным: верификация устройства на доставку не влияет. Номер устройства
берётся из тела device-announce / `keyx` и не сверяется с `senderDevice`
конверта, а для нового номера закреплённого identity нет
(`docs/psk_exchange.md` §3).

## 8. Взаимодействие с профилями безопасности

- `multiDeviceAllowed=false` по умолчанию (пресет «Параноик» и все, §8 ТЗ):
  линковка недоступна, device-announce от собственного аккаунта игнорируются.
  Включение — «ослабление»: подтверждение + предупреждение (больше устройств =
  больше поверхность атаки, каждое устройство — полноценный доступ к перепискам).
- Верификация отпечатка (§14.3) расширяется: safety-код теперь учитывает набор
  устройств; появление нового устройства у контакта показывается баннером
  «у контакта новое устройство — сверьте отпечаток». Баннер ставит только
  device-announce по control-каналу; устройство, добавленное через `keyx`, его
  не вызывает.

## 9. Влияние на backend: нулевое (и это by design)

Ключевое свойство протокола: **сервер менять не нужно.** Почему:

- Per-device mailbox-id — просто новые opaque идентификаторы, которые клиент
  выводит из HKDF. Сервер уже принимает любой валидный id (`validate_id`:
  8..64 url-safe base64) и работает как store-and-forward (MD-2).
- Проблема **деструктивного ack** (ack удаляет для всего mailbox — критично, если
  один mailbox слушают несколько устройств) **снимается автоматически**: у
  каждого устройства СВОЙ mailbox, оно ack-ает только свои сообщения. Никакого
  per-device курсора на сервере не требуется.
- Fan-out — целиком клиентский (sender-side); по самим id сервер не связывает
  ящики (разные HKDF-выводы неразличимы). Но `msgId` во внешнем конверте одинаков
  во всех копиях сообщения, а `senderDevice` открыт, поэтому сервер видит число
  устройств получателя и связывает их ящики (см. §12).
- TTL 7 дней (MD-7) уже действует на все mailbox одинаково.

Таким образом сама адресация не даёт серверу нового знания без единой доработки
релея — это прямое следствие capability-модели. Утечки через открытые поля
конверта и общую Tor-цепочку — отдельная проблема (§12).

> Единственное возможное будущее серверное улучшение (НЕ требуется для
> корректности) — «account fan-out mailbox», куда сервер сам размножает один POST
> по подписчикам. Мы его **сознательно не делаем**: это дало бы серверу знание о
> связи устройств (нарушение MD-2). Клиентский fan-out дороже по трафику, но
> строго сильнее по приватности.

## 10. Отзыв устройства (revoke)

- Пользователь на любом устройстве: «Отвязать устройство `dX`».
- Рассылается device-revoke: (а) своим устройствам по self-sync
  (`SelfSyncManager.revokeDevice`, `kind=revoke` — **реализовано §1.37**, с §1.39
  идёт двойным конвейером слой A→B, forward secrecy — см. §6.2),
  (б) контактам по control-каналу (`DeviceAnnouncer.revokeMyDeviceToContacts`).
  Все перестают fan-out на `dX`, помечают `revoked=true` (у моих устройств — в
  `DeviceSettings.linkedDevices`; если анонс `dX` ещё не дошёл, создаётся
  tombstone-запись `revoked=true`, чтобы поздний device-announce не «воскресил»
  устройство под тем же номером).
- **Известная ошибка (аудит 01.11.2026): отзыв обходится.** У контактов
  повторный device-announce записывается с `revoked=false` (`DeviceAnnouncer`), и
  upsert в `PeerDeviceStore` перезаписывает флаг — контакты снова начинают fan-out
  на отозванное устройство. Среди моих устройств tombstone защищает только тот же
  номер: `SelfSyncManager` принимает анонс с любым новым номером. Мнемоника, PSK
  и адреса ящиков при отзыве не меняются, поэтому отозванное устройство, у
  которого остались данные, может вернуться. Надёжный отзыв требует ротации PSK
  с контактами и адресов ящиков (а при утечке мнемоники — новой личности); это не
  реализовано.
- Локально на отзываемом устройстве при доступе — экстренная очистка ключей
  (crypto-shredding, §7.4): его Signal identity и PSK уничтожаются. **Честная
  граница реализации:** авто-crypto-shred при УДАЛЁННОМ отзыве (когда другое моё
  устройство сообщило `dX`, что он отозван) осознанно НЕ выполняется —
  деструктивное действие требует явного локального подтверждения; self-sync-revoke
  лишь распространяет флаг `revoked` по живым устройствам.
- **Честная граница:** отзыв — это «перестать слать/принимать», а не
  ретроактивная защита. Уже доставленные на `dX` сообщения там и остаются
  (E2EE-мессенджеры так и работают). Forward secrecy обеспечивается ротацией
  ratchet, а не отзывом.

## 12. Модель угроз и честные границы

- **Компрометация одного устройства** раскрывает переписки этого устройства (у него
  полный доступ). Это фундаментально для мультидевайса и честно показывается при
  включении (§8). Меньше устройств = меньше поверхность (поэтому default = запрет).
- **Сервер** по самим id ящиков их не связывает, но защита метаданных от него
  неполная (известное ограничение, аудит 01.11.2026): (1) `msgId` во внешнем
  конверте одинаков во всех копиях одного сообщения — выдаёт число устройств
  адресата и связывает их ящики; (2) `senderDevice` открыт; (3) все long-poll и
  дропы клиента идут через одну Tor-цепочку без изоляции, поэтому оператор
  релея может связать ящики пользователя и восстановить граф «кто-кому»
  (`docs/threat-model.md` §3.3).
- **Метаданные fan-out (тайминг/порядок).** N устройств → N дропов. Раньше они
  уходили практически одновременно и в детерминированном порядке (по возрастанию
  `deviceId`), поэтому глобальный наблюдатель за релеем мог по таймингу/порядку
  предположить групповую доставку. **Смягчено (§1.40):** `FanoutJitter`
  рандомизирует порядок per-device дропов и вносит случайную задержку перед каждым
  дропом; величина управляется `meta.minimize` (§8): `MAXIMUM` (Параноик) — до
  2.5 c на дроп, `MODERATE` — до 0.8 c, `BASIC` — выкл (прежнее поведение).
  Применяется единообразно ко всем каналам fan-out (переписка, control §14.2,
  сигналинг звонков §7.5, self-sync §6) через единый инстанс в [AppContainer],
  чтобы наблюдатель не различал типы трафика и «одно устройство vs несколько» по
  тайминг-паттерну. Против самого сервера это не помогает: тип трафика он читает
  из открытого `channel`, а групповую доставку — по общему `msgId`.
- **Метаданные fan-out (факт и объём отправки).** Даже с джиттером наблюдатель
  видел, ЧТО отправка произошла (всплеск POST-ов) и СКОЛЬКО было дропов (≈ число
  устройств-адресатов). **Смягчено (§1.41, вариант №3a):** `CoverTraffic` добавляет
  фиктивный трафик (обе меры — только при `meta.minimize=MAXIMUM`):
  (1) **фоновые decoy-дропы** через случайные интервалы (45–180 c) в рекуррентный
  пул decoy-mailbox — реальная отправка тонет в шуме, «молчит» не отличить от
  «пишет»; (2) **паддинг батча** — реальный fan-out разбавляется 0–3 фиктивными
  дропами. Decoy идёт тем же `POST /v1/mailbox/<id>`, mailbox-id того же формата
  (32 байта → url-safe base64 без паддинга, проходит `validate_id`), payload
  правдоподобного размера (256–1280 Б). **Ограничение:** для сервера decoy
  отличим от реального дропа — настоящий конверт это JSON (`{"type":…`), а decoy —
  случайные байты; decoy-ящики никто не опрашивает и не подтверждает, а число
  устройств и так выдаёт общий `msgId`. Поэтому против сервера cover-traffic не
  работает; против сетевого наблюдателя в режиме без Tor — частично (размеры
  пересекаются с короткими сообщениями), в режиме Tor трафик и так внутри Tor.
- **Общая честная граница (§1.40/§1.41):** это по-прежнему СМЯГЧЕНИЕ, а не
  устранение (общий предел store-and-forward). Constant-rate padding на мобильном
  непрактичен (батарея/трафик, §7.4), поэтому cover-traffic вероятностный и включён
  лишь в «Параноике»; глобальный пассивный наблюдатель с долгой статистикой всё ещё
  может вести трафик-анализ (напр. отличить одноразовые mailbox-паддинга от
  рекуррентных реальных — decoy-пул это лишь ослабляет). Основную защиту метаданных
  транспорта даёт Tor. E2EE (слои A/B) от джиттера/cover-traffic НЕ зависит,
  best-effort-доставка сохраняется; decoy не несёт реального контента, его никто не
  слушает, он истекает по TTL (MD-7).
- **Свою криптографию не вводим** (MD-5): только HKDF-SHA512 (адресация),
  libsignal (per-device сессии), Argon2id+каскад (пакет линковки). Джиттер и
  cover-traffic используют `kotlin.random.Random` — это не криптографический ГСЧ
  (для маскировки нужен `SecureRandom`, §6.1 ТЗ).
