# AEGIS — приём/отправка через релей (клиентская сторона), §7.6 / §12.2

> Согласовано с сервером `aegis-server`. **Авторитетное описание протокола** —
> `aegis-server/PROTOCOL.md`; здесь — как это устроено на клиенте.
>
> Релей один, транспорт к нему зависит от режима сети (`docs/tor_transport.md`
> §4): «Tor ВКЛ» — HTTP/1.1 через Tor к onion-адресу, «Tor ВЫКЛ» — HTTPS к тому же
> релею. API, конверты и шифрование одинаковы; перекрёстного отката нет.

## Адресация (§10.9)

Текущий клиент использует per-device адресацию v2 (`docs/multidevice.md` §4): у
каждого устройства свой входящий ящик

```
convInbox(PSK, ownerAccountId, ownerDeviceId) =
    HKDF-SHA512(salt="AEGIS/mailbox/v2", ikm=PSK, info="aegis/mailbox/v2/conv/<accountId>/<deviceId>")
```

Я **слушаю** свой `convInbox`, а **пишу** во входящие ящики всех активных
устройств собеседника. Исходная схема v1 — пара ящиков по роли 0/1
(`mailbox(role)`, `salt="AEGIS/mailbox/v1"`) — в клиенте удалена, примитив в ядре
сохранён.

По самим id сервер не может связать ящики с личностью или между собой, PSK в
сеть не уходит. Но метаданные от сервера защищены не полностью: все запросы
клиента идут через одну Tor-цепочку (по long-poll на каждый контакт), внешний
конверт несёт открытые поля (`channel`, `msgId`, `senderDevice`, признак слоя A),
длина не выравнивается — поэтому оператор релея может связать ящики
пользователя и восстановить граф «кто-кому» (`docs/threat-model.md` §3.3).

## Поток

- **Отправка:** `текст/CallControl → слой A (каскад на PSK) → слой B (Signal) →
  конверт JSON → POST /v1/mailbox/{outbox}` транспортом текущего режима
  (best-effort; E2EE уже выполнено локально до сети).
- **Приём:** `RelayReceiver` держит по одному long-poll на активный PSK-контакт
  (`GET /v1/mailbox/{inbox}?after&wait`), расшифровывает B→A и направляет по полю
  `channel` конверта: сигналинг звонка (`"call"` → `CallSignaling.onWire` →
  `CallManager.handleControl`), control-канал (`"control"` → `ChatSignals.onControl`)
  или обычный текст (`MessagePipeline.receive`); затем `ack`.
- Работает только при разблокированном аккаунте, доступном слое B и готовом
  транспорте: в режиме Tor — поднятый Tor и onion-адрес, без Tor — HTTPS-адрес
  релея. Адреса приходят из сборки и подписанного конфига или задаются в
  «Настройки → Сеть и Tor».

## Control-канал (§14.2 / §7.3)

Метаданные переписки идут ТЕМ ЖЕ конвейером `слой A → слой B → Tor` (конверт с
`channel="control"`), поэтому тип события и id сообщений скрыты внутри двойного
шифртекста. Открыто во внешнем конверте лишь то, что это служебное событие
(`channel="control"`), тип Signal-сообщения, признак слоя A и номер
устройства-отправителя; длина не выравнивается, так что тип события можно
пытаться угадать по размеру и ритму. Формат — `ControlMessage` (`type`: `read` | `typing` |
`presence` | `delete`). Общий id сообщения (`WireEnvelope.msgId`) позволяет обеим
сторонам ссылаться на одну запись в отчётах прочтения и «удалить у всех».
«Печатает…»/онлайн-статус на приёме — только в памяти (§10.10); отчёты прочтения и
удаление меняют зашифрованную БД. Все исходящие события уважают настройки
приватности (§14.2). Изменений на СЕРВЕРЕ не требуется — релей channel-agnostic
(хранит непрозрачный конверт).

## Вложения (§14.4, `/v1/blob/{id}`)

Файл шифруется каскадом **слоя A** на СВЕЖЕМ случайном 256-битном ключе (не PSK,
не через Double Ratchet) и грузится отдельным блобом (`RelayClient.putBlob` →
`PUT /v1/blob/{id}`, `id` — capability на 256 бит, генерирует клиент). Ключ,
`id` и метаданные (`AttachmentRef`) кладутся ВНУТРЬ сообщения и уходят обычным
конвейером `слой A(PSK) → слой B(Signal) → Tor`. Итог: сервер видит два
шифртекста (блоб и конверт-ссылку), не связанных по содержимому, — без plaintext
и личности. Связать их он может по времени и общей Tor-цепочке, а размер блоба
ему виден (выравнивания нет).

- **Отправка** (`MessagePipeline`): фаза 1 `createOutgoingAttachment` — сохранить
  байты в зашифрованную БД + вставить запись (PENDING), UI сразу показывает
  вложение; фаза 2 `uploadAndSendAttachment` — зашифровать блоб, `PUT`, затем
  отправить `AttachmentRef` в сообщении (SENT/FAILED).
- **Приём:** `receive` сохраняет `AttachmentRef` (без байтов). `downloadAttachment`
  качает блоб (`GET`), расшифровывает слоем A ключом из ссылки, кладёт байты в БД
  и шлёт `DELETE /v1/blob/{id}` (минимизация хранения §7.3). Мелкие медиа
  (≤ `ATTACHMENT_AUTO_DOWNLOAD_MAX_BYTES`) качаются автоматически при включённом
  `SecuritySettings.autoDownloadMedia`; иначе — по тапу «Скачать».
- Байты вложений хранятся BLOB'ом в SQLCipher (`attachments`) — plaintext на диск
  не пишется (§6.3); выбор файла — Photo Picker / SAF (`AttachmentReader`, без
  разрешений на хранилище и без временных файлов). Лимит отправки —
  `ATTACHMENT_MAX_BYTES` (8 МБ).

## Голосовые сообщения (§14.4)

Голосовое — **это вложение, а не новый канал**: маршруты релея не добавлялись
(`PROTOCOL.md §4.4b`). Отличия только клиентские.

**Запись** (`VoiceRecorder`) идёт целиком в памяти: `AudioRecord` (PCM 16 бит,
моно, 16 кГц) → `MediaCodec` (AAC-LC, 24 кбит/с) → кадры **ADTS** в `ByteArray`.
`MediaRecorder` не подошёл принципиально — он умеет писать только в файл/FD, то
есть незашифрованный звук неизбежно оказывался бы на диске; `MediaMuxer` (MP4)
по той же причине тоже исключён, а ADTS не требует мультиплексора, потому что
конфигурация декодера лежит в заголовке каждого кадра. Минута ≈ 180 КБ, потолок
длительности — `VOICE_MAX_DURATION_MS` (5 мин), при достижении запись
останавливается сама и отправляется.

**Огибающая** (`VoiceWaveform`) считается из того же PCM по ходу записи (пик на
отрезок `VOICE_WAVEFORM_STEP_MS`), сжимается до 56 уровней и едет в
`AttachmentRef.voice.waveformB64` — то есть под слоями A+B. Это позволяет
получателю нарисовать дорожку ДО скачивания блоба; иначе пришлось бы либо
показывать пустую полосу, либо декодировать AAC на каждый видимый пузырь.

**Воспроизведение** (`VoicePlaybackController`) — `MediaPlayer` поверх
`MediaDataSource` над массивом из SQLCipher: расшифрованный звук остаётся в
памяти (§6.3), временного plaintext-файла нет. Контроллер один на экран, поэтому
запуск нового голосового глушит предыдущее, а плеер освобождается при уходе с
экрана.

### Где живёт ОТКРЫТЫЙ звук — полный учёт (§6.3/§7.4)

Файла с незашифрованной записью не существует ни на одном шаге:

| Шаг | Где данные | Состояние |
|---|---|---|
| запись | RAM (`AudioRecord` → `MediaCodec` → `ByteArray`) | открыто |
| хранение | таблица `attachments` в SQLCipher (AES-256, ключ обёрнут Keystore/StrongBox) | зашифровано |
| отправка | блоб на релее | каскад слоя A на случайном ключе |
| ссылка | конверт mailbox | слой A(PSK) + слой B(Signal) |
| проигрывание | RAM (`MediaDataSource` → `MediaPlayer`) | открыто |

Ни `setOutputFile`, ни `MediaMuxer`, ни `cacheDir` в пути голосового не
участвуют — именно поэтому отвергнут `MediaRecorder`. Сравните со съёмкой на
камеру (`CameraCapture`), где временный JPEG на диске неизбежен и его приходится
затирать: у голосового такого компромисса нет.

Открытые байты в куче **затираются после использования**
(`MessagingRepository.sendVoice` и `VoicePlaybackController.release`) — та же
дисциплина, что `passphrase.fill(0)` в `AegisDatabase`. Плеер при этом работает на
СВОЕЙ копии: массив вызывающего кэшируется композицией пузыря и переиспользуется
при повторном «play», поэтому затирать чужой массив нельзя.

**Границы, которые эта схема НЕ закрывает** (честно, как §7.4 про NAND):

* Затирание в куче — best-effort. Сборщик мусора мог переместить массив, и его
  прежняя копия этим вызовом не затрагивается. Это сокращение окна экспозиции, а
  не гарантия.
* `MediaPlayer`/`MediaCodec` исполняются в **отдельных системных процессах**
  (`mediaserver`, `media.codec`): открытые байты пересекают границу процесса по
  binder, а декодированный PCM уходит в AudioFlinger. Это свойство любого
  воспроизведения звука на Android, а не нашей реализации (та же граница у
  превью видео через `VideoFrameDecoder`), и обойти её, оставаясь на системном
  декодере, нельзя.
* Противник с возможностью снять дамп памяти процесса всё равно сильнее этой
  защиты: в той же куче в этот момент есть ключ SQLCipher и состояние Signal.

Резервные копии и скриншоты закрыты на уровне приложения независимо от голосовых:
`allowBackup=false`, `fullBackupContent=false`, `data_extraction_rules` исключает
всё содержимое, `FLAG_SECURE` включён принудительно на всех экранах приложения,
кроме экрана сканера QR библиотеки ZXing (§14.3).
Уничтожение мастер-ключа (`KeyStoreManager.destroyAllKeys`, §7.4) мгновенно
делает нечитаемыми и записи голосовых — они лежат в том же файле БД.

**Автозагрузка:** голосовое приходит как `kind = FILE` (совместимость, см.
`PROTOCOL.md §4.4b`), но `maybeAutoDownload` качает его наравне с медиа — иначе
сообщение, которое пользователь ждёт готовым к нажатию «play», требовало бы
лишнего тапа. Порог `ATTACHMENT_AUTO_DOWNLOAD_MAX_BYTES` (2 МБ) при этом
соблюдается и заведомо покрывает любую запись в пределах потолка длительности.

**Разрешение:** `RECORD_AUDIO` уже объявлено в манифесте (звонки, §7.5); для
записи запрашивается runtime-разрешение отдельным шлюзом (`rememberMicPermissionGate`)
— тянуть `CAMERA` через `rememberCallPermissionRequester` ради звука было бы
непрошеным расширением прав. Foreground-сервис НЕ поднимается: запись живёт
только пока экран на переднем плане, а уход в фон её отменяет (с Android 14
микрофон в фоне без FGS типа `microphone` беззвучно отдаёт нули, и отправить
тишину хуже, чем не отправить ничего).

## TURN для звонков (§7.5, `GET /v1/turn`)

Клиент запрашивает у релея эфемерные TURN-креды (`RelayClient.getTurn` →
`GET /v1/turn`, см. `PROTOCOL.md §4.5`) транспортом текущего режима:

- **Tor ВКЛ:** из ответа берутся `{onion, port, username, credential}`.
  `TurnProvisioner` поднимает `TorTcpForwarder` (`127.0.0.2:<port>` →
  SOCKS5(Tor) → `<coturn>.onion`) и отдаёт `CallManager`/`WebRtcMediaEngine`
  единственный ICE-сервер `turn:127.0.0.2:<port>?transport=tcp`. Поля `uris` и
  `stun` игнорируются. Нет `onion` — звонок не начинается.
- **Tor ВЫКЛ:** берутся `uris` (запасной вариант — `stun`) только на домене
  HTTPS-адреса релея (`CallIcePlan.clearnetServers`) и отдаются WebRTC напрямую,
  без форвардера.

Медиа остаётся E2EE (DTLS-SRTP + кадровый слой) — coturn релеит только
шифртекст. Секрет TURN клиенту не раскрывается (только производные креды на срок
`ttl`).

## Границы v1

- Один long-poll на переписку; мультиплексирование — в планах.
- Без серверной аутентификации ящика (capability = знание mailbox-id из PSK).
- TURN/медиа звонков через Tor (§7.5) — РЕАЛИЗОВАНО (см. выше). Реалтайм через Tor
  имеет высокую задержку/потери — осознанный компромисс режима Tor.
- В режиме без Tor сервер видит IP клиента и может сопоставлять его с адресами
  ящиков (честно сказано в диалоге выключения Tor).
