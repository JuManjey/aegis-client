# AEGIS — звонки (P8, §7.5 / §10.10): архитектура и согласование с backend

> Требования — §7.5, §10.10 технического задания.
> Здесь — фактическая реализация звонков в клиенте и контракт для `aegis-server`.

Звонки (голос/видео) построены на **WebRTC (DTLS-SRTP)** — аудированном стандарте
защиты медиапотока. Свою медиа-крипту и свой транспорт мы НЕ пишем (§1). AEGIS
добавляет к WebRTC два независимых усиления и заворачивает сигналинг в тот же
E2EE-конвейер слоёв A → B, что и текст (без PSK-обёртки A1S1, которая есть
только у сообщений переписки).

---

## 1. Модель безопасности (§7.5 / §10.10)

Медиа защищает DTLS-SRTP. Поверх этого AEGIS обеспечивает **аутентичность сторон и
анти-MITM недоверенного сервера** двумя механизмами:

1. **Корень ключей — через Signal-сессию (слой B).** Инициатор генерирует
   случайный 256-битный `callSecret` (ОС-ГСЧ) и передаёт его собеседнику ВНУТРИ
   offer'а, зашифрованного тем же конвейером, что и текст: **слой A (каскад на
   PSK) → слой B (Signal) → Tor → onion-релей**. Сервер/сеть видят только двойной
   шифртекст; `callSecret` наружу не выходит.

2. **Ручной PSK (§6.2) подмешивается** в вывод ключей звонка как соль HKDF. Даже
   если сервер полностью контролирует раздачу ключей и подменил Signal-сессию
   (MITM), он не знает out-of-band PSK → не воспроизведёт ни ключи кадрового
   слоя, ни код сверки SAS.

Из `callSecret` + `PSK` + `callId` + «транскрипта» согласования (отсортированные
DTLS-фингерпринты обеих сторон, привязка к конкретному TLS-каналу) выводятся:
- два независимых ключа кадрового слоя по направлениям (i→r и r→i), по 256 бит.
  Ядро выводит их в формате AES-256 SRTP (ключ + 112-бит соль), но соль не
  используется, а сами ключи идут только в `FrameCryptor`, который сводит их к
  128 битам (§5). DTLS-SRTP ключуется собственным рукопожатием DTLS, на проводе
  согласуется `AES_CM_128_HMAC_SHA1_80`;
- короткий код сверки **SAS** (3 группы по 4 цифры) для устной сверки в начале
  разговора — как «safety number», но для звонка.

Симметрия ролей: `send` инициатора == `recv` собеседника и наоборот.

### Вывод ключей (Rust `calls.rs`, только фича `signal`)

Две ступени HKDF-SHA512 (крейт `hkdf`, разделение доменов):

```
root(64B) = HKDF-SHA512(salt = PSK, ikm = callSecret, info = "aegis/call/root/v1")

i2r = HKDF-SHA512(salt = 0, ikm = root, info = "aegis/call/srtp/i2r/v1" ‖ 0x1f ‖ callId ‖ 0x1f ‖ context)
r2i = HKDF-SHA512(salt = 0, ikm = root, info = "aegis/call/srtp/r2i/v1" ‖ 0x1f ‖ callId ‖ 0x1f ‖ context)
sas = HKDF-SHA512(salt = 0, ikm = root, info = "aegis/call/sas/v1"      ‖ 0x1f ‖ callId ‖ 0x1f ‖ context)
```

`context` — отсортированный список `a=fingerprint:` из обоих SDP. Тесты (8 шт.)
проверяют: согласие сторон, независимость направлений, влияние PSK/`callSecret`/
`callId`/`context` на ключи и SAS, длины ключей, JSON-сериализацию.

JNI-граница: `nativeCallDeriveKeys(callSecretB64, pskB64, callId, initiator,
contextB64)` → JSON `{sendKey, sendSalt, recvKey, recvSalt, sas}` (ключи base64).
Kotlin-фасад — `com.aegis.crypto.CallCrypto.deriveKeys(...)`.

## 2. Клиентские компоненты (`:app`, пакет `call`)

| Компонент | Роль |
|---|---|
| `CallManager` | Машина состояний (`IDLE→DIALING/RINGING→CONNECTING→ACTIVE→ENDED`), координация сигналинга и медиа, вывод и применение ключей, извлечение DTLS-фингерпринтов из SDP в `context`, лента этапов для UI. Состояние — только в памяти (минимизация метаданных, §10.10). |
| `CallSignaling` | Шифрует/отправляет и расшифровывает `CallControl` тем же конвейером, что текст (слой A→B→Tor). |
| `MediaEngine` | Интерфейс медиадвижка, изолирует `org.webrtc.*` от остального кода. |
| `WebRtcMediaEngine` | Реальный WebRTC (DTLS-SRTP): `PeerConnectionFactory`, аудиодорожка, **видео (Camera2-захват 720p, локальный предпросмотр + рендер собеседника через `SurfaceViewRenderer`, переключение/выкл камеры)**, offer/answer, ICE. |
| `PlaceholderMediaEngine` | Заглушка, если нативный WebRTC недоступен: сигналинг/ключи/SAS без медиапотока, `onConnected()` не вызывается, UI честно показывает отсутствие WebRTC. |
| `CallAudioSession` | Единый владелец режима аудио (`MODE_IN_COMMUNICATION`) и аудиофокуса со счётчиком ссылок — движок и тоны держат сессию одновременно (см. §3.7). |
| `CallTonePlayer` / `CallToneController` | Гудки и служебные тоны: синтез из патчей `:core-common` и правило «фаза → тон» (см. §3.7). |
| `CallRingtonePlayer` | Рингтон и вибрация входящего: URI (персональный/системный) либо встроенный синтезированный тон. |

Фабрика в `AppContainer` пытается поднять `WebRtcMediaEngine`, при неудаче честно
откатывается на `PlaceholderMediaEngine`; факт отражается в UI (`CallScreen`,
секция настроек «Звонки»).

Зависимость: `io.github.webrtc-sdk:android` (Maven Central; исходники WebRTC
открыты, §1). В APK — `libjingle_peerconnection_so.so` в обеих ABI.

## 3. Маршрут медиа выводится из режима сети

Отдельного переключателя «медиапоток через Tor» больше нет: маршрут медиа следует
режиму сети (`docs/tor_transport.md` §4). Сигналинг звонка всегда идёт тем же
транспортом, что и сообщения. План ICE строит чистая функция
`CallIcePlan.forMode(mode, servers)` — её проверяют JVM-тесты, а движок только
исполняет готовый план.

| Режим | Политика ICE | ICE-серверы | Тайминги ICE | Что видит пара |
|---|---|---|---|---|
| **Tor ВКЛ** (по умолчанию; «Параноик», «Баланс») | `RELAY` | один: `turn:127.0.0.2:<port>?transport=tcp` — локальный форвардер в onion coturn | под RTT Tor | только coturn; IP скрыт Tor |
| **Tor ВЫКЛ** (только вручную, через диалог) | `ALL` | `stun:`/`turn:`/`turns:` своего сервера из `uris` в `GET /v1/turn` | обычные WebRTC | IP друг друга и серверу (согласие в диалоге выключения Tor) |

RTP работает по UDP, а Tor несёт только TCP, поэтому в режиме Tor весь
медиатрафик идёт через TURN по TCP через Tor. Ни STUN, ни host-кандидатов, ни
серверов вне loopback: всё это ушло бы мимо Tor. `CallIcePlan.forMode` для
режима Tor принимает только `turn:` по TCP на `127.*`; любой другой набор
серверов — `RelayRequiredException`, и звонок не начинается с причиной
«Ретранслятор через Tor недоступен…» (fail-closed).

В режиме без Tor relay-кандидат имеет самый низкий приоритет ICE: при наличии
прямого пути выигрывает он, а TURN/TURNS своего сервера — резерв, когда прямого
пути нет (симметричный NAT, VPN, изоляция клиентов). Серверы берутся только на
домене HTTPS-адреса релея или его поддоменах (`CallIcePlan.clearnetServers`):
публичный STUN третьей стороны получил бы IP пользователя, а недоверенный сервер
не должен направлять телефон в loopback, локальную сеть или onion-имя через
системный DNS. Если серверов нет, звонок идёт только на host-кандидатах (в одной
локальной сети), а этап TURN помечается предупреждением.

### 3.1 Собеседники в разных режимах

Клиент с Tor собирает только relay-кандидат, клиент без Tor — host, srflx и
relay. Соединяется пара relay↔relay: обе аллокации живут на одном coturn, адрес
ретрансляции у него внутренний (`external-ip` не задаётся), и пересылка между
аллокациями — доставка внутри сервера. Поэтому для звонков «Tor ↔ без Tor» на
сервере нужен клирнет-профиль (`aegis-server/README.md`, раздел «Клирнет-профиль»): без него
клиент без Tor не получает TURN, и звонок с клиентом в режиме Tor не соединится.

**Уровень защиты не понижен.** Медиа под DTLS-SRTP плюс кадровый слой на ключах
Signal+PSK (§5); coturn ретранслирует только шифртекст и ретранслирует только в
собственные аллокации (не открытый прокси). Аренда TURN берётся ПАРАЛЛЕЛЬНО с
поднятием FGS микрофона. В режиме Tor её ждут столько, сколько нужно (relay —
единственный путь). Без Tor ожидание ограничено бюджетом
(`TURN_DIRECT_BUDGET_MS`, 7 с **от начала подготовки движка**, а не от конца
ожидания FGS — иначе задержки складывались бы): если аренда не успела, звонок
идёт без неё, а опоздавшая аренда закрывается.

**Требование к backend.** Режим Tor: TURN на релее (`AEGIS_TURN_SECRET` +
`AEGIS_TURN_ONION`, `aegis-server/README.md`, раздел «TURN для звонков»). Режим без Tor:
клирнет-профиль и `AEGIS_TURN_PUBLIC_URIS` (раздел «Клирнет-профиль» там же). Проверка:
`curl -fsS https://<домен>/v1/turn` — `404` означает «TURN выключен», пустой
`uris` — «клирнет-серверы не раздаются».

**Во время звонка режим не меняется:** переключатель Tor недоступен, пока идёт
звонок, — медиа не может сменить маршрут посреди разговора, а при смене режима
все аренды TURN закрываются (`TurnProvisioner.closeAll`).

### Как медиа идёт через Tor (реализовано, §12.2)

WebRTC не умеет ходить в TURN через SOCKS-прокси Tor, поэтому клиент строит мост:

1. `TurnProvisioner` (пакет `call`) запрашивает у релея эфемерные TURN-креды —
   `RelayGateway.fetchTurn()` → `RelayClient.getTurn()` → `GET /v1/turn` через Tor.
   Ответ: `{onion, port, username, credential, realm, ttl}` (см.
   `aegis-server/PROTOCOL.md §4.5`). Секрет TURN клиенту НЕ раскрывается.
2. Поднимается локальный `TorTcpForwarder` (`:network-tor`):
   `127.0.0.2:<localPort>` → SOCKS5(Tor) → `<coturn>.onion:port` (не
   `127.0.0.1` и не свой WLAN-IP: оба пути дают native SIGSEGV в TurnPort на
   Samsung / Android 15–16). Каждое TCP-соединение WebRTC туннелируется в Tor
   отдельным каналом.
3. Движку отдаётся ICE-сервер `turn:127.0.0.2:<localPort>?transport=tcp` с этими
   кредами (`WebRtcMediaEngine(appContext, plan)`), политика `RELAY`. Обе стороны
   звонка релеят медиа через один coturn.

Аренда (`TurnProvisioner.Lease`) создаётся у инициатора при звонке, у
принимающего — при приёме (не на звонок, который отклонят), и закрывается в
`CallManager.endCall` (форвардер гасится). Если релей/TURN недоступны (нет
`GET /v1/turn`, Tor не поднят, форвардер не запустился) — аренда пустая. Без
Tor звонок идёт без резерва. В режиме Tor он **не начинается**:
`CallManager.prepareEngine` прерывает установку с причиной «Ретранслятор через
Tor недоступен…» и отправляет собеседнику `hangup`, этап TURN помечается
отказом. Раньше движок в этом случае создавался с политикой `ALL` (RELAY с
пустым списком серверов роняет `network_thread`), собирал host-кандидаты и
отдавал локальные IP собеседнику, а в одной сети медиа шло напрямую мимо Tor.
Страховка на случай другого пути в движок —
`WebRtcMediaEngine.createPeerConnection` отказывается создавать соединение с
планом Tor, в котором нет TURN через форвардер.

## 3.5 Жизненный цикл на устройстве: FGS, блокировка, отзывчивость

Три системных ограничения Android определяют, как звонок ведёт себя на реальном
телефоне. Все они уже привели к полевым дефектам, поэтому зафиксированы здесь.

### FGS микрофона — жёсткое предварительное условие

Android 14+ не даёт поднять `AudioRecord` без foreground-service типа
`microphone`, а сам такой FGS разрешено запускать только когда приложение
«видимо» (while-in-use доступ к микрофону). Если `startForeground()` отказал,
контракт `startForegroundService()` остаётся невыполненным, и через несколько
секунд система убивает процесс
`RemoteServiceException$ForegroundServiceDidNotStartInTimeException` — снаружи
это «приложение закрылось сразу после нажатия Принять».

Поэтому `CallMediaService`:
* объявляет типы FGS только под **фактически выданные** разрешения (тип
  `microphone` без `RECORD_AUDIO` — гарантированный `SecurityException`);
* при неудаче обязательно делает `stopSelf()` — снимает контракт;
* отдаёт исход (`READY`/`DENIED`/`TIMEOUT`), а не «всегда готов».

`CallManager.ensureMediaService` делает одну повторную попытку (окно «приложение
ещё не видимо» после нажатия из уведомления — сотни миллисекунд) и при отказе
**прерывает звонок с понятным текстом**, а не поднимает медиа, которое всё равно
будет убито.

### Пересоздание Activity не должно гасить звонок

`AppContainer` живёт на процесс, а корневой composable — на Activity, и
`AegisRoot` вызывает `container.initialize()` из `LaunchedEffect(Unit)`. Значит
`initialize()` прилетает повторно при каждом создании Activity: поворот экрана,
смена темы, свайп приложения из списка недавних при живом процессе (его держит
foreground-service приёма).

Поэтому оба `initialize()` обязаны быть идемпотентны к живой сессии:

* `AccountManager.initialize()` НЕ понижает `Unlocked` до `Locked`. Понижение
  означало «аккаунт заблокировали»: `AppContainer` по `Locked` останавливает
  приём и делает `callManager.hangUp()` — то есть звонок обрывался ровно в
  момент нажатия «Принять» после свайпа приложения из недавних. Исчезновение
  записи аккаунта — наоборот, повод сбросить состояние (внешнее стирание §7.4).
* `AppContainer.initialize()` выполняется один раз на процесс: повторный прогон
  заново распечатывал восемь настроек ключом Keystore и поднимал вторые копии
  фоновых циклов. Её зовёт и `MessageSyncService` — система перезапускает
  сервис после выгрузки процесса без интерфейса, и без инициализации он видел
  аккаунт `None` и останавливал приём. Одновременный второй вызов ждёт первого.

### Экран блокировки

Окно звонка показывается поверх блокировки, пока есть звонок — живой или
звонящий при закрытом аккаунте: `MainActivity.applyLockScreenFlags` в `onCreate`
(синхронно, до первого кадра) и подписка на состояние ставят
`setShowWhenLocked`/`setTurnScreenOn` и снимают их через 3 с после звонка,
объявлено `USE_FULL_SCREEN_INTENT`. Это и удобство (принять, не разблокируя
телефон), и обход проблемного пути выше. Атрибуты манифеста нужны только для
холодного старта full-screen intent'ом; без звонка `onCreate` их сразу снимает.
Раньше до первого звонка действовали именно они: оставленное открытым приложение
вставало поверх блокировки при каждом включении экрана, показывая переписку без
PIN телефона, а автоблокировка по возврату закрывала аккаунт и останавливала приём.

Скрытность §14.3 сохраняется на уровне содержимого, а не окна: пока
`KeyguardManager.isKeyguardLocked` (`rememberDeviceLocked`), `CallScreen` рисует
обезличенную карточку — без имени контакта, кода сверки SAS, деталей этапов и
видео собеседника. Во время звонка остальной интерфейс поверх блокировки не
показывается: оверлей звонка непрозрачен и занимает весь экран. `FLAG_SECURE`
включён для всех экранов `MainActivity` и здесь не отключается.

Оговорка (вывод по коду, на устройстве не проверялся): оверлей исчезает сразу по
окончании звонка, а флаги «поверх блокировки» снимаются только через 3 с
(`LOCK_SCREEN_GRACE_MS`). Если автоблокировка аккаунта до звонка не наступила
(прошло меньше таймаута или она выключена), отложенной блокировки нет, и
разблокированное приложение около 2 с видно и доступно поверх экрана блокировки
телефона. Если блокировка была отложена на время звонка, она применяется сразу
по его окончании — тогда окна нет.

Автоблокировка аккаунта (§14.3) **уступает** живому звонку: `IdleLockController`
не блокирует в середине набора/ICE/разговора, а откладывает блокировку до конца
звонка (`onBusyFinished`). Иначе блокировка рвала приём и Tor на середине
согласования и уводила UI на экран входа в момент нажатия «Принять». Таймер
бездействия идёт только пока приложение на экране: запущенный после звонка в
фоне, он закрывал аккаунт через минуту («Параноик»), и вместе с аккаунтом
останавливался приём следующих звонков.

### Отзывчивость: действия пользователя не ждут сеть

Один POST в релей через Tor занимает секунды, поэтому пользовательские действия
никогда не стоят в очереди за сетью:

| Действие | Что происходит синхронно | Что уходит в фон |
|---|---|---|
| «Принять» | рингтон и вибрация стоп, уведомление снято, фаза → `CONNECTING` | FGS, TURN, движок, `answer` в релей |
| «Сбросить» / «Отклонить» | фаза → `ENDED`, окно закрывается (220 мс) | `hangup` в релей, `MediaEngine.close()` (ждёт поток WebRTC до 5 с), закрытие аренды TURN |

Пауза перед закрытием окна зависит от инициатора: своё действие читать не нужно
(220 мс), чужой сброс или ошибку — нужно (1200 мс).

⚠️ `DiagnosticLog.sync` пишет в файл **синхронно**, поэтому на UI-потоке его
вызывать нельзя. Для этого `CallManager` разделён на `publishPhase` (дешёвое
обновление состояния, безопасно везде) и `logPhase` (журнал, только из корутин и
нативных потоков).

## 3.6 Лента этапов звонка (UI)

`CallInfo.stages` — хронологическая лента `CallStageEntry(stage, state, atMs,
detail)`, которую ведёт `CallStageLog` (`:core-common`, покрыт юнит-тестами).
`CallScreen` рисует её бабблами мессенджера (`AegisHudBubble`) с отметкой
«+1.4 с» от начала звонка и маркером состояния: идёт / пройден / оговорка /
отказ.

Зачем: соединение через Tor и ICE занимает секунды, и одна надпись
«Соединение…» не отличает «ждём ответа релея» от «ищем сетевой путь» и от «путь
не нашёлся». Этапы: набор/входящий вызов → служба микрофона → TURN → медиадвижок
→ параметры шифрования → доставка приглашения/ответа через Tor → ключи и SAS →
поиск сетевого пути → медиа под DTLS-SRTP → завершение.

Правила ленты (§10.10): живёт **только в памяти**, сбрасывается на каждый новый
звонок, ограничена 24 записями, повторная отметка «идёт» обновляет запись на
месте (а не плодит строки), и в неё НЕ попадают адреса, onion, `ufrag`, ключи и
отпечатки — только ярлыки этапов и короткие человеческие пометки. На
заблокированном экране пометки скрыты, ярлыки видны.

Сюда же выведены два состояния, которые раньше выглядели как зависание: «медиа
идёт через резервный ретранслятор» (`onIcePath` → тип пары `relay`) и «путь
потерян, восстанавливаем» (ICE `DISCONNECTED`; фаза при этом остаётся `ACTIVE` —
звонок не сброшен).

### Таймауты установки

Разделены по фазам, потому что фазы ждут разного:

| Фаза | Бюджет | Причина завершения |
|---|---|---|
| `DIALING` / `RINGING` | 75 с | «Нет ответа» |
| `CONNECTING` (Tor ВЫКЛ) | 45 с | «Не удалось соединиться: сеть не пропускает медиапоток» |
| `CONNECTING` (Tor ВКЛ) | 75 с | то же |

**Zero-trust (§10.9):** медиа остаётся E2EE (DTLS-SRTP) — coturn ретранслирует
только шифртекст. В режиме Tor пиры приходят из Tor (реальный IP скрыт), coturn
опубликован отдельным Onion Service v3 (не тем же, что релей) → сервер не
связывает трафик релея и TURN между собой.

Отдельной настройки маршрута медиа нет: он следует режиму сети (§3). Раздел
«Настройки → Звонки» только показывает, как пойдёт медиа при текущем режиме.

## 3.7 Звуковое оформление звонка (гудки и тоны)

До этого раздела звонок был **беззвучным везде, кроме входящего**: рингтон вёл
`CallRingtonePlayer`, а исходящий вызов, согласование и завершение проходили в
полной тишине — пользователь не мог отличить «идёт дозвон» от «приложение
зависло». Теперь ход звонка озвучен.

### Откуда берётся звук: синтез, а не ассеты

Ни одного файла в `res/raw` не добавлено. Тоны **синтезируются на лету** из
декларативных «патчей»:

| Файл | Модуль | Роль |
|---|---|---|
| `call/tone/CallTone.kt` | `:core-common` | Перечисление тонов, маршрут вывода, модель патча (`ToneVoice`, `CallToneSpec`) |
| `call/tone/CallTonePalette.kt` | `:core-common` | Сам звуковой дизайн: патч на каждый тон |
| `call/tone/CallToneSynth.kt` | `:core-common` | Рендерер: патч → моно PCM 16 бит, 48 кГц |
| `call/CallTonePlayer.kt` | `:app` | Воспроизведение через `AudioTrack` (`MODE_STATIC` + аппаратная петля) |
| `call/CallToneController.kt` | `:app` | Подписчик `CallManager.state`: фаза → тон |
| `call/CallAudioSession.kt` | `:app` | Владелец режима аудио и фокуса со счётчиком ссылок |

Почему синтез:

1. **Воспроизводимая сборка.** У проекта есть проверка детерминированности
   (`reproducible-build.yml`); ноль бинарных ассетов — ноль поводов для
   расхождения артефактов. Звук задан кодом и проверяется JVM-тестом.
2. **Размер APK и F-Droid.** Девять зацикленных мелодий в 48 кГц — это мегабайты;
   патч занимает десятки строк.
3. **Никаких новых зависимостей** (§1): нужен только `kotlin.math`.

Синтезатор — «модульный» в миниатюре: осциллятор (`SINE`/`SQUARE`/`SAW`/
`TRIANGLE`/`NOISE`) + расстроенный второй осциллятор (`detuneHz`) + трапецеидальная
огибающая + тремоло + кольцевая модуляция + намеренное прореживание
(`downsample`, sample & hold) и квантование (`bitcrushBits`). Последние два и дают
«цифровую грязь», из которой собран стиль приложения; шум берётся из
собственного xorshift64 с зерном из патча, поэтому рендер **детерминирован
побитово**.

### Палитра

| Тон | Когда | Характер |
|---|---|---|
| `OUTGOING_RINGBACK` | `DIALING`, исходящий (петля) | «Гудки»: два расстроенных импульса с нисходящим глиссандо, цифровой чирп, шум эфира; каденция 3.2 с |
| `NEGOTIATING` | `CONNECTING` (петля) | Тихие «пинги рукопожатия» — фаза через Tor длится секунды, и тишина читается как зависание |
| `CONNECTED` | вход в `ACTIVE` | Восходящая квинта — «канал открыт» |
| `LINK_LOST` | `ACTIVE` + `reconnecting` (петля) | Дрожащий сигнал тревоги, тихо — речь собеседника может вернуться |
| `RELINK` | снятие `reconnecting` | Короткий восходящий блип |
| `HANGUP` | `ENDED`, код `ENDED`/`NONE` | Нисходящее «отключение питания» |
| `BUSY` | `ENDED`, код `BUSY` | Двухтональный зуммер 480/620 Гц с кольцевой модуляцией |
| `DENIED` | `ENDED`, коды `DECLINED`/`TIMEOUT`/`UNREACHABLE`/`ERROR` | Два резких нисходящих удара |
| `INCOMING_RING` | входящий звонок | Арпеджио ля-минора с субпульсом и шиммером — подпись приложения |

Каденции намеренно остались телефонными («гудок — длинная пауза», «занято —
частые удары»): узнаваемость сигнала важнее стиля.

Одно исключение из правил: переход `RINGING → ENDED` **не озвучивается**.
Пропущенный или отклонённый входящий звонок ни разу не стал разговором, и тон в
ухо здесь неуместен — телефон просто перестаёт звонить, как в любой телефонии;
обратную связь о пропуске даёт уведомление.

### Маршрутизация и приватность (§10.10)

Тоны хода звонка идут по **каналу разговора** (`USAGE_VOICE_COMMUNICATION`): в
ухо, громкостью вызова, с учётом гарнитуры/Bluetooth. Это не только привычное
поведение телефонии, но и минимизация наблюдаемости: узнаваемый тон AEGIS из
громкоговорителя — это метаданные, которые слышат окружающие. Громко звучит
только рингтон входящего (`USAGE_NOTIFICATION_RINGTONE`) — в этом его смысл.

### Владение аудиосессией (важное исправление)

Режим `MODE_IN_COMMUNICATION` и аудиофокус — ресурсы **процесса**, и раньше ими
владел `WebRtcMediaEngine` в своих `enterCallAudio`/`leaveCallAudio`. Это давало
два дефекта, устранённые вводом `CallAudioSession` (счётчик ссылок, единый
владелец):

1. **Режим мог «залипнуть».** Каждый движок запоминал `previousAudioMode` у себя.
   Если новый звонок начинался до того, как догорел `close()` предыдущего (а тот
   ждёт поток WebRTC до 5 с), второй движок запоминал как «прежний» уже
   `MODE_IN_COMMUNICATION` и после звонка не возвращал систему в норму.
2. **Гудки не могли звучать раньше движка.** Первый `AudioTrack` фиксирует
   маршрут в момент создания: без заранее выставленного режима разговора тон
   начинался в громкоговорителе и через секунду перескакивал в ухо.

Заодно тип фокуса исправлен на `AUDIOFOCUS_GAIN_TRANSIENT_EXCLUSIVE` (как в
телефонии): чужое воспроизведение **приостанавливается и возобновляется** после
звонка, а не получает постоянное «остановись насовсем», как при прежнем
`AUDIOFOCUS_GAIN`. Аварийный путь — `CallAudioSession.reset()`, вызывается при
блокировке аккаунта, чтобы режим не переживал звонок ни при каком сбое.

### Причина завершения как код

Тон завершения нельзя было выбрать по `CallInfo.endReason`: это локализованная
строка для человека, сравнивать её в коде — значит сломать логику при первой
правке перевода. Поэтому добавлен `CallInfo.endCode: CallEndCode`
(`ENDED`/`DECLINED`/`BUSY`/`TIMEOUT`/`UNREACHABLE`/`ERROR`), который заполняет
`CallManager.endCall(...)`. Побочно исправлен «мигающий» кадр: причина завершения
теперь публикуется тем же обновлением состояния, что и фаза `ENDED`, а не
следующим — раньше наблюдатели успевали увидеть «завершено, причина пустая».

### Настройки (§14.5)

Оба переключателя живут в `NotificationSettings` (независимые пользовательские
настройки, в сравнение пресетов §8 не входят), раздел «Настройки → Уведомления»:

| Настройка | По умолчанию | Смысл |
|---|---|---|
| `callSynthRingtone` | `true` | Встроенный рингтон вместо системного. Персональная мелодия контакта (§14.5) всегда важнее |
| `callProgressTones` | `true` | Гудки и тоны хода звонка |

`callProgressTones` намеренно НЕ подчинён `callSound` и режиму звонка устройства:
`callSound` управляет звонком телефона (канал рингтона), а «без звука» на
устройстве глушит звонок, но не звук уже идущего разговора.

Поля добавлены с дефолтами, а `SecureStore` декодирует с `ignoreUnknownKeys` —
поэтому обновление и откат версии переживают файл настроек без миграции.

### Два источника рингтона страхуют друг друга

Мелодия входящего берётся либо из URI (`MediaPlayer`), либо из синтеза
(`AudioTrack`), и **сбой одного источника переключает на другой**:
`URI → синтез`, `синтез → системная мелодия`. Сбой здесь не гипотетический: URI
может указывать на удалённый файл или на провайдера без прав, а созданию
`AudioTrack` может не хватить свободной дорожки. Беззвучный входящий звонок —
это пропущенный звонок, поэтому вторая попытка обязательна; синтез стоит
последним резервом осознанно — ему не нужны ни файл, ни разрешения, ни сторонний
провайдер.

Поэтому `CallTonePlayer.startLoop` возвращает `Boolean`: владелец рингтона обязан
отличать «играет» от «молчит». У тонов прогресса резерва нет и не нужно — там
молчание это неудобство, а не пропущенный звонок.

## 4. Контракт с backend (§0 / §12.2, zero-trust)

Сигналинг звонка — это `CallControl`, упакованный в тот же конверт, что текстовые
сообщения. Через onion-релей проходит только двойной шифртекст:

```jsonc
// CallWireEnvelope (в сеть уходит именно это)
{
  "type": "...",           // тип конверта слоя B (Signal)
  "layerA": true,          // применён ли каскад на PSK (слой A)
  "ciphertextB64": "...",  // двойной шифртекст (A→B), base64
  "senderDevice": 1,       // номер устройства-отправителя (выбор ratchet), открыт
  "channel": "call",       // маркер канала для демультиплексирования (виден серверу)
  "v": 1
}
```

Внутри (после расшифровки B→A) — `CallControl`:

```jsonc
{
  "type": "offer|answer|ice|hangup|busy",
  "callId": "<uuid>",
  "media": "AUDIO|VIDEO",
  "callSecretB64": "...",  // только в offer; КОРЕНЬ ключей звонка
  "sdp": "...",            // offer/answer SDP (содержит DTLS-фингерпринт)
  "ice": "sdpMid|idx|cand",// ICE-кандидат (для type=ice)
  "reason": "..."          // для hangup/busy
}
```

**Сервер/релей НЕ видят** SDP, ICE, `callSecret`, SAS, тип звонка — всё это
внутри E2EE. Роль релея — доставка непрозрачных конвертов (как для текста).
Метка `channel = "call"` лежит во внешнем конверте открытым текстом: по ней
закрытый аккаунт звонит, ничего не расшифровывая, но и сервер может отличить
сигналинг звонка от сообщения (не видя содержимого и личности отправителя —
только номер его устройства). Длина конвертов не выравнивается.

**Правила приёма.** `CallSignaling.onWire` отвергает конверт с `layerA = false`,
если с контактом есть PSK (`PskManager.requireLayerA`; то же в переписке и
control-канале). Легитимный отправитель с PSK всегда накладывает слой A, а без
PSK не может даже вывести адрес ящика, — значит, такой конверт подделан тем,
кто подменил Signal-сессию (TOFU), и без проверки он прошёл бы в обход каскада.
`CallManager` отвергает offer, где секрет звонка не 256 бит, и принимает
answer/ice/hangup с id текущего звонка только от его собеседника.

Живой ПРИЁМ сигналинга из релея (long-poll/mailbox) подключается вместе с backend:
метод `CallSignaling.onWire(contact, wireJson)` уже расшифровывает входящий конверт
B→A и возвращает `CallControl` для `CallManager.handleControl(...)`.

### Видео (ГОТОВО)

`switchCamera`.

### Дополнительный кадровый слой поверх DTLS-SRTP — ГОТОВО (§1.14)

Каждый медиа-кадр звонка дополнительно шифруется НЕЗАВИСИМЫМ AEAD на ключах
звонка (`CallCrypto.CallKeys` из Signal+PSK) поверх DTLS-SRTP — второй,
независимый слой шифрования медиа (defense-in-depth, §4). Ключа кадрового слоя
НЕТ в DTLS-рукопожатии: компрометация DTLS-SRTP или подмена согласования
недоверенным сервером не раскрывает медиа, пока цел out-of-band корень
(`callSecret` из Signal-канала) и ручной PSK.

**Почему не C++ `FrameEncryptorInterface` из отдельного `.so`.** Предсобранный
`io.github.webrtc-sdk:125.6422.07` вызывает AddRef/Encrypt по vtable объекта
из ЧУЖОГО `.so` (`libaegis_frame.so`) → SIGSEGV ~1 с после принятия звонка.
Навешивать этот шим нельзя, уровень защиты при этом не понижается: тот же AAR
уже содержит `org.webrtc.FrameCryptor`, скомпилированный в
`libjingle_peerconnection_so.so` (тот же native-образ, что и PeerConnection).

**Реализация (без форка WebRTC, §1).**

- `CallFrameCryptor` ставит `FrameCryptorFactory.createFrameCryptorForRtpSender/Receiver`
  с `FrameCryptorAlgorithm.AES_GCM` и 32-байтными ключами направления
  (`sendKey`/`recvKey` из HKDF-SHA512, корневой материал 256 бит из
  Signal+PSK). На проводе — **AES-128-GCM**: `KeyProvider` webrtc-sdk M125
  прогоняет ключ через PBKDF2-SHA256 (100 000 итераций, соль
  `aegis/call/frame-cryptor/v1`) до 128 бит и выбирает AES по длине ключа
  (`SetKeyFromMaterial` → `DeriveKeys(…, 128)`); AES-256 этим API не получить.
  Имена участников стабильны по направлению (`aegis-i2r` / `aegis-r2i`).
- `RTCConfiguration.cryptoOptions`: `enableGcmCryptoSuites=true` лишь добавляет
  GCM-наборы. DTLS-SRTP на практике согласует **`AES_CM_128_HMAC_SHA1_80`**: в
  M125 он первый в списке у обеих сторон, BoringSSL берёт первый подходящий из
  списка сервера, а Java-API не даёт его отключить. Слабый AES-128-SHA1-32
  выключен.
  `requireFrameEncryption=false`: этот флаг проверяет `FrameEncryptorInterface`,
  а не `FrameTransformer`. При `true` WebRTC дропал RTP поверх уже навешенного
  FrameCryptor (ICE CONNECTED без звука). Fail-closed — сбой навески завершает
  звонок; `discardFrameWhenCryptorNotReady` отбрасывает кадр без ключа.
- Проводка: `WebRtcMediaEngine.applyDerivedKeys` навешивает криптор на все
  `RtpSender` и `RtpReceiver` (новые — в `onAddTrack`). Если навесить не
  удалось или нативный слой звонков недоступен, `CallManager.deriveAndApply`
  бросает `CallSetupException`: установка прерывается (принимающий не
  отправляет answer, собеседник получает `hangup`), а не откатывается на
  «только DTLS-SRTP».
- Порядок у обеих сторон — ключи до медиа. Принимающий навешивает криптор до
  отправки answer, звонящий — до `setRemoteDescription(answer)`: на прямом пути
  ICE и DTLS сходятся за десятки миллисекунд после применения ответа, и
  навешенный позже криптор пропускал бы первые кадры без кадрового слоя. По той
  же причине звонящий публикует `CONNECTING` до применения ответа — после
  `ACTIVE` он откатил бы разговор назад.
- Журнал: webrtc-sdk пишет на уровне INFO байты исходного и производного ключа
  (`raw_key […] derived_key […]` в `DerivePBKDF2KeyFromRawKey`). Такие строки
  `WebRtcMediaEngine.logNative` отбрасывает целиком
  (`CallTrace.carriesKeyMaterial`) — и из журнала, и из нативных «крошек».
- `rust/.../frame.rs` (ChaCha20-Poly1305) остаётся эталоном и покрыт тестами;
  C++-шим `aegis_frame.cpp` не навешивается (ABI-ловушка prebuilt WebRTC).

Обе стороны звонка должны быть на этой версии клиента: приёмник без кадрового
дешифратора не декодирует кадры. Это свойство доп. слоя, не ослабление.

### TCP-TURN через Tor — ГОТОВО (§12.2)

Медиапоток в режиме Tor реализован end-to-end: backend отдаёт эфемерные
TURN-креды (`GET /v1/turn`) к coturn за отдельным onion, клиент поднимает
локальный TCP-форвардер в Tor и передаёт WebRTC ICE-сервер
`turn:127.0.0.2:<port>?transport=tcp` (см. раздел 3 выше и
`aegis-server/PROTOCOL.md §4.5`, `aegis-server/README.md`, «TURN для звонков»). Реалтайм-медиа через Tor
имеет высокую задержку/потери — это осознанный компромисс режима Tor. В режиме
без Tor клиент получает STUN/TURN/TURNS того же coturn напрямую (`uris`,
`aegis-server/README.md`, «Клирнет-профиль»).
